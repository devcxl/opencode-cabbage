# 开发场景 SOP 索引

本目录收录当前功能开发主流程（`setup → requirements → design → tasks → code → review → release`）之外、常见开发场景的标准方法论（SOP）。每个场景一份文档，聚焦「标准做法 + 在本项目 How to 落地」。

## 为什么需要

现有主流程是**单线、面向新功能开发**的流水线。对 Bug 修复、紧急修复、业务调整、重构、基础设施变更等场景，它强制套用 `PRD → 设计 → DAG → 并行` 的重量模型，存在严重过载；部分场景（如 Corrective Flow）仅有术语、无落地。

本 SOP 系列的目标：为每个非功能场景提供**场景识别 → 走哪条路径 → 复用哪些现有资产 → 验证门禁**的明确指引，避免「一律走功能流」。

## 场景分派总览

> **说明**：本目录是供人阅读/维护的方法论文档，**不随插件分发**。运行时权威分派逻辑内置在 primary agent（`assets/agents/dev-lifecycle.md` 的 Phase 0 场景分诊）中；下表与之一致，若改动请同步。

| 输入 / 现象 | 场景 | SOP | 路径特征 |
|-------------|------|-----|----------|
| 新功能开发 | 功能流 | 主流程（既有） | 全流程 |
| 已合并代码回归、行为不符合预期 | Bug 修复 | `01-bug-fix` | 轻量，跳过需求/设计/任务 |
| 线上 P0/P1 缺陷，需立即发版 | 紧急修复 | `02-hotfix` | 最短路径 + 立即 patch 发版 |
| 既有功能行为/字段/交互调整 | 业务调整 | `03-business-adjustment` | 变更管理 + 兼容/迁移 |
| 不改行为、只改结构 | 重构 | `04-refactor` | 行为保持 + 测试安全网 |
| 死代码/技术债清理 | 技术债清理 | `05-tech-debt` | 盘点 + 行为保持移除 |
| CI/依赖/配置/构建链路变更 | 基础设施变更 | `06-infra-change` | CI 即验收 |
| 文档新增/修改 | 文档更新 | `07-docs-update` | Docs-as-Code + 术语一致 |
| 发布回滚、Flow 异常收尾 | 回滚与异常 | `08-rollback` | 回滚策略 + 受控收尾 |

## 通用原则

- **复用优先，新增其次**：能复用 `flow-tdd`、`flow-code`、`flow-review`、`flow-release`、goal 工具、Worktree Lifecycle 的，不另起炉灶。
- **轻重两档**：行为变更类场景按严重度/影响选择全流程或轻量路径；非行为类场景（重构/技术债/基础设施/文档）天然轻量。
- **Slug 前缀扩展**：现有体系以 `feat/<slug>` 为唯一分支命名，且 `flow-tasks` 将 `fix-bug` 列为反模式。非功能场景需扩展前缀为 `fix/<slug>`、`hotfix/<slug>`、`refactor/<slug>`、`chore/<slug>`、`docs/<slug>` 等，与 `feat/` 并列。
- **验证优先**：每个 SOP 定义可执行的验证门禁，不依赖「感觉做对了」。
- **术语一致**：新领域术语写回根 `CONTEXT.md`；技术债/迁移等结构决策如需长期约束，补 `docs/adr/`。

## 待落地缺口

以下是为使上述 SOP 可用而需要新增的流程资产（当前缺失，属后续设计工作，非本系列文档范围）：

- 场景分派入口（识别输入类型并路由到对应 SOP）
- `flow-corrective` skill 与 `/fix` 命令
- Hotfix 最短路径与 patch 发布通道
- 重构「行为保持」审查轴
- 异常收尾（cancel/blocked/回滚）流程
